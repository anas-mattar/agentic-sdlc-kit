## Findings

### F1 — `-Row` and `-As` prefix-bind in a description, so FR-011's "byte-identical without `-Row`" is not strictly true — CONFIRM

`scripts/claim-feature.ps1:36-37`. `FeatureDescription` is `ValueFromRemainingArguments`, so before this change any dash-led word in the description went into the description. PowerShell binds unique-prefix parameter names, so `-R`, `-Ro`, `-A` and `-As` now bind. Observed with stub scripts using the old and new `param` blocks: `claim-feature.ps1 -ShortName x -A foo desc` formerly gave a description `-A foo desc` and now gives `-As foo` with description `desc`; `... a -As b` loses `-As b` from the description; a description whose last word is `-As`/`-Row`/`-R` now fails with "Missing an argument for parameter" where it used to claim. Without `-Row` the `-As` value is also silently ignored (no fit read, no message). The scenario is narrow (a description that contains a bare `-A`, `-R`, `-As` or `-Row` word, for example "Add -As flag to the CLI"), and it changes the feature's description or refuses, which FR-011 says it never does. Plain words, `Row` without a dash, `-Json`, `-NoPush`, `-ShortName` and the exit codes are unchanged. A positional description before `-Row` also works.
*Action: owner decision. Either accept and record the limit in the phase 4 guidance and `notes.md` ("a description that contains a bare `-A`, `-R`, `-As` or `-Row` word must be quoted or passed after `--`... which this script does not support"), or reword FR-011 to "for every call that does not pass `-Row`/`-As` and whose description holds no dash-led word". A fixture pinning one such call would make the choice visible. Not blocking.*

### F2 — The advisory guarantee has no containment: an exception in `Get-ClaimFit` aborts the claim before allocation — MINOR

`scripts/claim-feature.ps1:131-146`. `$ErrorActionPreference = 'Stop'` is in force and the Fit block is not inside `try/catch`. Everything I could feed it returned a kind (see evidence), because `Get-DeveloperMode` and `Get-RoadmapRows` catch their own reads. But nothing guarantees that for the next edit to those functions, for a malformed record shape the doctor has not yet been taught, or for the dot-source itself (a syntax error or a partial lib would stop the claim, where the same script has a branch for "lib not found"). The spec says the note "never changes the claim"; an unhandled exception would refuse a claim, with a PowerShell error rather than a `Stop-Refused` line, and nothing was claimed. `@(...Roster)` would also produce a one-element `@($null)` if a future roster were `$null`, and `$d.Name` on it yields a bogus Unplaced line rather than an error.
*Action: implementer, optional follow-up inside phase 3 territory: wrap the dot-source and the call in `try { ... } catch { $fit = @{ Kind = 'Unreadable'; Cause = "the fit could not be read: $($_.Exception.Message)" } }`, and add one fixture whose `kit-adoption.json` or roadmap makes the reader throw if one can be built (else a unit test that stubs `Get-ClaimFit`). Not blocking: no failing input found.*

### F3 — A cell of ASCII `-` (or a repeated name) is read as a repository, and a duplicate prints twice — MINOR

`adoption-lib.ps1`, `Get-RoadmapRows`, the filter `$_ -and $_ -ne [string][char]0x2014`. The contract says an empty cell or an em dash declares nothing, and the template uses the em dash. The same templates and all the fixtures' Owner cells show that adopters write `-` as often. A Repos cell of `-` becomes a repository named `-`: a claimant who lists any repos then gets `Fit: row 'X' declares -; ada does not list -; listed by: no one declared it`. A row `web, web` prints `declares web, web; ... does not list web, web`. A cell with a backtick-quoted pipe splits at the pipe (the GAP-015 lesson applies, the reader only handles `\|`). All are advisory-note noise, not a verdict change.
*Action: implementer: treat `-` like the em dash, de-duplicate `Declared`/`Uncovered` case-insensitively, and add one fixture (a `-` cell) to `FIT-001`. Not blocking.*

### F4 — Plan P6 names a pure `Get-RepoFit`; what shipped is `Get-ClaimFit`, which reads files, and the record does not list it as a deviation — DOC DRIFT

`tasks.md` Phase 3 purpose and T018 say "`Get-RepoFit` is the one reader of `repos`" and give `-Roster -Claimant -Repos`, a pure function, plus a row reader. The commit ships `Get-ClaimFit -Root -Row -Claimant` (reads the roster and the roadmap itself, so the unit is not testable with a plain roster object), with a different set of kinds from the P6 list (`Match` becomes `None`, `NoDeclaration` is folded into `None`, three read kinds added). `notes.md` records the T016 and `FIT-007` deviations but not this one, and its "the only reader of a roster entry's `repos`" claim is true. The behaviour matches the contract.
*Action: implementer: add the rename, the loss of purity and the folded kinds to the notes' deviation list. No code change required.*

### F5 — Fixture gaps: the cases pass, but four stated behaviours are pinned by nothing — MINOR

(a) `pass-names-compare-loosely` varies only the roadmap side (` Web ` against `web`); the claimant side (`-As GRACE`, `-As ' grace '`) is not exercised, though the code trims and ignores case there. (b) An empty Repos cell is not pinned (only the em dash). (c) `-Json` is not pinned: the notes say a fixture was removed because of path normalisation, and the silence under `-Json` rests on `Write-Fit` going through `Write-Info`; an edit of `Write-Fit` would not fail any case. (d) `FIT-005` covers a missing roadmap but not one that exists and cannot be read, and the "lib not found" branch has no fixture (the rule note admits it). Also `FIT-001/fail` and the variants assert exit 0 and the claim lines, which does cover "the claim is unchanged" (the notes' `FIT-007` claim is right).
*Action: implementer: add an `-As` case/space variant, an empty-cell variant, and a `-Json` variant whose expected text avoids the path (for example `-Json` with `noRoot` and only the `BRANCH_NAME`-free keys), or record (c) as a known gap. Not blocking.*

### F6 — The fit is read from the local working tree, which may be behind origin — MINOR

`Get-RoadmapRows -Root $repoRoot` reads `docs/roadmap.md` and `kit-adoption.json` from the checked-out `main`. The script has just run `git fetch origin --prune` but not merged, so a roadmap row added by a teammate on origin since the last pull gives `0 roadmap rows match` (a named line, so honest), and a roster edit not yet pulled gives a stale cover. No claim is affected.
*Action: none for this phase; say it in the phase 4 guidance ("pull before claiming with `-Row`"). Optionally the note could name the commit it read.*
