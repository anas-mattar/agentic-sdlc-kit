## Findings

### F1 — The exemption reason of SCOPE-032 and REPOS-037 is false: rev-list can fail after merge-base succeeds — CONFIRM

`rules.json` (SCOPE-032 `exemption`, REPOS-037 `exemption`), `plan.md` P5 and `notes.md` T002(c) say `git rev-list <base>..HEAD` "can fail only on objects `git merge-base` has just walked, so every damage tried fails the merge base first", and that the lines are "defence in depth". That holds on the harness fixtures (no commit-graph), not on a real repository. With a commit-graph (`git gc` writes one by default, as do many hosts and tools), `merge-base` reads ancestry from the graph and never opens the tip commit object, while `rev-list` resolves `HEAD` through the object:

```
git commit-graph write --reachable; truncate the loose tip commit object to half its bytes
git merge-base HEAD main                 -> prints the base, exit 0
git rev-list --no-merges main..HEAD      -> error: corrupt loose object ..., exit 128
```

Run through the scripts (scratch repos M and R3): parent `scope-check.ps1 -All` -> `UNGRADED (no commits since merge base - no commit was examined)`, exit 0; tip -> `ERROR could not list the commits since the merge base (git rev-list failed with exit 128) ...`, exit 1; `scope-check-repos.ps1` likewise (`repo-a: ERROR could not list ...`, exit 1). So the two rev-list lines are the only thing that makes a commit-graph repository with a damaged tip red, which is exactly the spec's User Story 2, and they are exercised in practice. The code is right; the written reason is not, and spec FR-007 requires an exemption to carry a true written reason of the kind feature 015 FR-004 asks for. No recipe field writes a commit-graph (`FixtureRepo.psm1`), so the exemption itself may stand, but not for this reason. The Phase 2 Territory (`adoption/updating.md`, `docs/roadmap.md`, `docs/digests/**`) does not cover `tests/**`, so the fix belongs in a phase 1 follow-up commit or an approved territory amendment.
*Action: owner decides before the gate: (a) correct the exemption text in `rules.json`, the P5 paragraph of `plan.md` (an amendment, approver recorded) and `notes.md` T002(c) to say that the state needs a commit-graph the harness cannot write, and drop "defence in depth"; or (b) better, add a `commitGraph` recipe step to `FixtureRepo.psm1` (inside `tests/**`) and real `SCOPE-032` and `REPOS-037` fixture pairs, using the repro above, which fails on the parent and passes at the tip. Either way tell phase 2's `adoption/updating.md` note that the commit-list ERROR is reachable.*

### F2 — A broken ref file is read as "no such ref" and stays UNGRADED, exit 0 — MINOR

`git rev-parse --verify --quiet <ref>` exits 1, not 128, for a ref file whose content is garbage (git prints `warning: ignoring broken ref` on stderr, which the scripts discard). With `refs/heads/main` overwritten by garbage and no `origin/main`, scratch repo Z prints `UNGRADED could not resolve a merge base with main - nothing checked`, exit 0 on parent and tip. `ritual-checks` is still green for a damaged trunk ref, the same defect class the feature closes for objects. The plan's premise that exit 1 means "absent" is true for a missing ref and untrue for a corrupt one; the spec's stated limits do not mention it.
*Action: add it to the stated limits (phase 2's `adoption/updating.md` note and `notes.md`); optionally follow up by also testing `git show-ref --verify` or reading the `rev-parse` stderr, in a later feature.*

### F3 — Two readable-but-odd states now ERROR instead of UNGRADED (unborn HEAD with a trunk present, a trunk that is a tag of a tree) — ACCEPTED

`scope-check.ps1 -All -Branch 001-thing` with an unborn `HEAD` (orphan checkout, no commit yet) and `origin/main` present: `git merge-base HEAD origin/main` exits 128 (`Not a valid object name HEAD`), so parent printed `UNGRADED ... nothing checked`, exit 0 and tip prints `ERROR could not read the merge base with main (git merge-base failed with exit 128)`, exit 1 (scratch repo H). The same for a `main` that is a tag of a tree (F). Neither is a case a numbered feature branch with phase commits reaches in CI (the branch has a tip), and "git could not do the read" is true of both, which plan P8 states for any non-damage failure. FR-006's "byte for byte for every readable repository" is therefore not literally true for them, since an unborn HEAD is a readable repository.
*Action: none; accepted under plan P8. If the owner wants FR-006 literal, special-case `git rev-parse --verify --quiet HEAD` exit 1 as "no commits, UNGRADED".*

### F4 — A later candidate's base silently wins over an earlier candidate's failure — ACCEPTED

`Get-DiffBase` and `Get-RepoMergeBase` return the base of `main` when `origin/main` could not be read (scratch repo J: `origin/main` points at a deleted object, `rev-parse` exit 0, `merge-base` exit 128, `main` is graded, no line printed). The plan's Risks section records this as a choice. If local `main` is stale the base is older, so the range is a superset: no branch commit is missed, but other features' commits in the superset can be graded against this feature's Territory (a spurious FAIL, never a spurious PASS). The failure on `origin/main` is invisible to the owner.
*Action: none for this phase. A later feature could print a `WARN` line for the earlier failure.*
