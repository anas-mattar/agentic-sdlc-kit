## Findings

### F1 — The note and `notes.md` describe the sample as "two with a phase token, one without, one merge" per project; it is true for ExpenseTracker only — DOC DRIFT

`adoption/updating.md` ("What was measured": "four commits chosen once from each project's own history (two with a phase token, one without, one merge)") and `notes.md` T010 (same words) overstate the sample. From the saved outputs: FitForge's four are `not applicable (no 'phase N' token)` x2, `PASS phase 8 (1 file(s))` and a merge, so one phase commit; FlowBoard's are `not applicable` x2, a merge and one `WARN commit ac75f1a: no territory declared for phase 7`, so no graded `PASS` at all; ExpenseTracker's are `PASS phase 1 (2 file(s))` x2, one token-less, one merge. The parenthetical after "byte-identical" (`a PASS of 1 or 2 files, not applicable ..., a WARN ...`) does describe the kinds seen, but the earlier "two with a phase token" does not hold, and SC-002 ("a passing phase commit ... print the same bytes ... on a clone of each adopted project") is carried for FlowBoard only by the WARN line and the fixtures. "Byte-identical" itself is true. An adopter reading the note would assume two graded phase commits per project.
*Action: implementer rewords both places to say what each project contributed (FitForge one graded phase commit, FlowBoard none graded and one WARN, ExpenseTracker two) and notes in `notes.md` that SC-002 for FlowBoard rests on the fixtures; no re-run needed.*

### F2 — Limit (1) does not say that `ritual-checks` and CI are the callers that use `-All` — DOC DRIFT

The note says a commit whose object is missing "can still end a `-All` run" on `UNGRADED ... exit 0`. That is accurate (I reproduced it) but never says that `scripts/ritual-checks.ps1:150` runs `scope-check.ps1 -All`, so the CI run of an adopted project is exactly where this limit applies, and that "What an owner may newly see" (the `ritual-checks` member reported as failed) is true for a damaged tree and not for a missing commit object. The GAP-040 row says "a CI run that grades a damaged branch is green", which is the sentence an adopter needs; the note, which is the adopter-facing text, omits it.
*Action: implementer adds one sentence to limit (1): `ritual-checks.ps1` and the CI that runs it grade with `-All`, so on a branch whose commit objects are missing the member prints `UNGRADED` and is not red; the remedy is the same `git fsck` / fresh clone.*

### F3 — "One such line per damaged commit" understates how many lines one damage produces — MINOR

The note ("What an owner may newly see") says that with `-All` there is one `ERROR` line per damaged commit. In my scratch repository, removing a single tree object printed four `ERROR` lines under `-All`: the commit whose tree it was, an empty commit sharing that tree, and the next two commits (each reads its parent's tree in its own diff). The phase 1 review had observed two lines for one damage. The sentence is literally true if "damaged" means "unreadable", but an owner who deletes one object will see several lines and may suspect more damage than exists.
*Action: implementer adds "a single damaged tree can be named on every commit that shares it and on its child commit" to the sentence; no code change.*

### F4 — The wrapper-facing change is not announced the way feature 031's note did — MINOR

Feature 031's note had a sentence for wrappers ("If a wrapper of yours matched git's ` ! [rejected]` line ... match the `--porcelain` line instead"). Here a wrapper that matched `PASS ... (0 file(s))` or `not applicable` for a damaged commit now sees `scope-check: ERROR commit <sha7>: ...` and exit 1, with no `PASS` line and no `not applicable` line; one that counted `PASS` lines in `-All` output will see fewer. The "What to do about it" paragraph says only how to react to the line. The messages are said not to be machine-parsed (limit 4), which covers it in spirit, and exit code 1 is what every failing commit already gave, but a wrapper author gets no direct sentence.
*Action: implementer adds one sentence to "What to do about it": a wrapper that treated `PASS (0 file(s))` or `not applicable` as the result for every commit should key on the exit code, and expects the `ERROR` line in their place for a damaged commit.*

### F5 — "1828 on the changed code" is a phase 1 working-tree number, not re-run at the tip — MINOR

The roadmap entry says "the harness 1809 passed on the parent and 1828 on the changed code". `notes.md` T007 takes 1828 from "Phase 1 working tree", before the follow-up commits (`d02ecc9` LF restore, `64ba0c8` wording and exemption text). *Action: none required before merge; T011's result replaces the number in `notes.md`. If it differs, implementer corrects the roadmap entry in the same commit.*
