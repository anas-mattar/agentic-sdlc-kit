## Findings

### F1 — `scope-lib.ps1` and `scope-check-repos.ps1` were rewritten from LF to CRLF — DOC DRIFT (hygiene; non-blocking)

At the parent all three scripts are LF (0 carriage returns in `8f31ab9:scripts/scope-lib.ps1` and `scope-check-repos.ps1`); at the tip `scope-lib.ps1` has 218 of 218 lines CRLF and `scope-check-repos.ps1` 418 of 418 (`scope-check.ps1` stays LF, 0). The repository is overwhelmingly LF (`git ls-files --eol`: 2939 LF, 35 CRLF, 25 mixed). So the real change in those two files is 18 and 6 lines (`git diff --ignore-cr-at-eol`), but the commit shows 420 and 830, the phase's `git diff --stat` reads as 1,228 insertions/622 deletions, `ritual-checks` warns that the commit "changes 1850 line(s) across 28 file(s)", and `git blame` on both scripts now points at this commit. Behaviour is unaffected (PowerShell, `update-kit` and `build-digests` normalise CRLF; the full `SCOPE-`/`REPOS-` runs pass), and FR-005's "byte for byte" concerns the scripts' output, not their source. It is an unrelated edit, outside what the plan asked for ("nothing else changes"), and a flow-down hazard: these are `verbatim` class in `kit-manifest.json`, so adopters receive the line-ending flip. The cause is most likely a Windows-side edit tool.
*Action: implementer re-saves `scope-lib.ps1` and `scope-check-repos.ps1` with LF line endings in a fixup commit on this branch (or the owner accepts the noise in writing in phase 2's notes); no code change needed.*

### F2 — T002(d) is ticked although `notes.md` says it was not run — DOC DRIFT

`tasks.md` ticks T002 `[x]`, whose item (d) is "the same probes on the CI image's git (the CI run of the branch is the second git)". `notes.md` T002(d) says "the CI image's git is the CI run of the branch (the second git); not run here." The tick therefore claims completion of something the record says is pending. The plan's first-task requirement to re-measure on the CI git is also the only portability evidence for the exit-code behaviour on the image the check actually runs on. The risk is small (a git whose `show` exits 0 on an unreadable tree would also fail `SCOPE-028..030` on the CI run, loudly), but the tick should be honest.
*Action: implementer amends `tasks.md` T002 to name (d) as pending the branch's CI run, or records the CI run's result once it exists; the owner approves the amendment (constitution I; the implementer must not approve their own).*

### F3 — Other reads can still turn damage into a green run; the spec's "stated limits" are accurate but incomplete — CONFIRM

The spec lists as limits: the `tasks.md`/`spec.md` blob reads (they FAIL with the wrong cause) and the committer-date read of `scope-check-repos.ps1` (it ERRORs). Those statements are accurate (I confirmed the blob reads still end in `FAIL`, not `PASS`). The spec does not list these, which I found by reading and, for the first, by running:
- `-All`: with the phase commit object itself deleted from a scratch repository, `scope-check.ps1 -All` printed `scope-check: UNGRADED could not resolve a merge base with main — nothing checked` and exited **0** (`Get-DiffBase`, `scope-check.ps1:81-93`, discards git's errors). The same hazard exists at `git rev-list --reverse --no-merges "$base..HEAD" 2>$null` (`:319`, an empty list prints `UNGRADED (no commits since merge base)`, exit 0) and at the matching read in `scope-check-repos.ps1:379`. A damaged commit graph therefore hides the damaged commits that the new ERROR would have named. This is a different read from the one the feature fixes, and `-Commit` on the same commit does give the new ERROR (observed).
- `git rev-list --parents -n 1` (`:118`) and `git log -1 --format=%s` (`:156`) with `2>$null` and no exit check: an unreadable commit object yields an empty parent list (treated as non-merge) or `$null` subject; the guard's `git show` (which runs first for non-merge) catches it, so no PASS results, but an unreadable **merge** commit would print `not applicable (... is a merge commit)` only if the parent read succeeded, which it would not. Low risk and consistent with merges being out of scope.
- The spec/tasks blob reads pass to Standard/`FAIL` with a wrong cause, as the spec says.
The spec's claim "`-All`, `-Commit` and `-Phase` do not change: they select commits, and an unreadable one is named wherever it is reached" is true for a commit reached; it is not true for a commit the selection step cannot list.
*Action: owner decides whether the `-All` selection reads (`Get-DiffBase`, `:319`, `scope-check-repos.ps1:379`) are a follow-up feature (recommended: record as a new GAP in `docs/roadmap.md` in phase 2, with the observed `UNGRADED`, exit 0) or stated as a limit in `spec.md`/`adoption/updating.md`; no change to this phase.*

### F4 — The `REPOS-035` exemption reason is supported only for the damage the author tried — MINOR

The reason says every damage tried breaks `git show -s --format=%cI` first. I could not construct a counter-example: in scratch repositories a deleted commit tree, a deleted *parent* tree (the child's own tree intact) and a deleted blob (the added side of a rename) all made `git show -s --format=%cI` exit 128 as well as `git show --name-status`, so the date read at `scope-check-repos.ps1:191-195` does fail first, and the reason is true for every case I tried. `git show -s` evidently still loads what the diff would, which is why. The reason is a measured fact about this git (2.55), not a property of the code: a git, or a damage, for which `show -s` stops short of the diff would reach the new line. The line is correct (`ERROR cannot read the changed files of <sha7>`, `'FAIL'`, in the shape of the date-read line), is inventoried so it cannot be reworded unnoticed, and the exemption text already says "defence in depth". It would be more robust if the reason named the git version measured.
*Action: none required; optionally add "measured on git 2.55.0.windows.5" to the exemption text in phase 2.*
