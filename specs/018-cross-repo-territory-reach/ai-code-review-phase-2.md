## Findings

### F1 — Ungraded plus a stale-only overlap prints no verdict word — MAJOR

`scripts/territory-check.ps1:118-134`. The `UNGRADED —` verdict is printed only inside `if ($overlaps.Count -eq 0)`.
When something was not compared and the only overlaps are stale (`$liveOverlap` false, exit 0), the output is the
overlap block, the `UNGRADED: governance: ...` line, then `Only stale claims overlap — consider adopting them...`.
There is no `UNGRADED —` line and nothing says "this is not a clean result"; the run exits 0 and the reader sees a
stale-claim hint that reads as a complete result. D2 as stated in the tasks ("otherwise any entry makes the run
`UNGRADED`") and the contract ("the verdict line when anything was not compared and nothing overlaps") do not fully
decide this case; `OVERLAP` the verdict word should mean a *live* overlap (exit 2), so a stale-only run with ungraded
entries should most plausibly end `UNGRADED`. `-Json` is correct here (`CLEAN` false), so text and JSON disagree about
whether the run was complete only in what they say. No fixture covers it (`fail-overlap` uses a live overlap).
*Action: author. Branch on `$liveOverlap`, not `$overlaps.Count`, for the verdict (or print the UNGRADED verdict line
whenever `$ungraded.Count -gt 0 -and -not $liveOverlap`, keeping the stale guidance after it), and add a hand-written
`TERR-013` fixture: a stale overlap plus a skipped claim, exit 0. If the owner reads D2 the other way, record the reading
in `notes.md` instead. Because D2 is an approved document, the choice is the owner's if it changes wording.*

### F2 — The `detail` and `cause` assert a reason the code has not established — MINOR

`territory-check.ps1:84-85`. The entry's `detail` is always `no remote-tracking ref origin/<other>`, but the branch is
taken on any non-zero exit of `git rev-list --count "$BaseBranch..origin/$other"`; that also fails when `$BaseBranch`
itself does not exist locally or the ref is corrupt. The message would then name the wrong cause. The pre-existing
warning says only "cannot compare with $BaseBranch", which is the safe wording.
*Action: author, either say `cannot compare with $BaseBranch (no origin/$other ref or no merge base)` or test
`git rev-parse --verify origin/$other` before choosing the detail. Fixtures only exercise the missing-ref cause.*

### F3 — No fixture for the plural count or a second ungraded entry — MINOR

All TERR-013 cases have exactly one ungraded entry, so `$($ungraded.Count)` and the order of several `UNGRADED:` lines
are untested; the text "(1 comparison(s) not made..." could be a constant and every test would still pass.
*Action: author, in `tests/**`: one case (or extend `fail`) with two skipped claims, expected text hand-written
(`2 comparison(s)`), both text and JSON.*

### F4 — A stale sentence survives in the TERR-012 rule notes — DOC DRIFT

`rules.json` TERR-012 `notes` still says "Both directions exit 0 and print CLEAN; ... That CLEAN is itself a finding ...
not changed here", then appends "CHANGED in feature 018 phase 2". The two statements contradict each other for a reader
who stops at the first. The `summary` and the recipe `description` were updated correctly.
*Action: author, trim the earlier sentences to past tense ("were") or remove them; `tests/**` only.*

### F5 — Script help and the 003 contract still describe the old exit/verdict set — DOC DRIFT

`territory-check.ps1:12-15` ("Exit codes: 0 clean (no live overlap)") does not mention the ungraded outcome, and the
`-Json` output shape is not described there. The script is in Territory; the 003 contract is not and the 018 contract
already extends it. *Action: author, one sentence in the `.DESCRIPTION`.*

### F6 — `no remote` JSON lacks `UNGRADED` (contract wording versus plan D3) — NOTE

The contract says `UNGRADED` is "always present" in `-Json`; line 52 still emits only `BRANCH/CLEAN/OVERLAPS` for the
no-remote state, which plan D3 and T008 require be untouched (TERR-006/007 `fail` directions confirm). Both are
defensible; the unchanged state is the approved choice. *Action: owner, none required; record in `notes.md` that
"always present" means "on every run that compares", so phase 3 does not "fix" the no-remote path by accident.*
