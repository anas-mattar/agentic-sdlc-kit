## Findings

### F1 — A short or non-string unknown recorded value now crashes the "delivered once" NOTE, after the record is written — CONFIRM

`update-kit.ps1:331` builds the recovery hint with `$recordedCommit.Substring(0,7)`. On the parent this line was unreachable for an unknown recorded value, because the failed `git log` left the surgical report empty. At the tip an unknown value now produces surgical entries, so the line runs, and it throws for any value shorter than 7 characters or that is not a string. Reproduced on a scratch kit with a surgical file, real run (no `-DryRun`): `.kit-version` `"kitCommit": "abc"` printed the Surgical section, then `Exception calling "Substring" with "2" argument(s): "Index and length must refer to a location within the string"`, exit 1, and `.kit-version` had already been rewritten to the kit's HEAD (`:274-281` runs before the report). Same for `"kitCommit": 123` and `true`. The parent printed `Result: up to date`, exit 0 for each (the silent defect this feature fixes, so the output is now more right than before), but the exit code is now 1, not "2 while anything is pending", and the doctor never runs. A hand-edited or corrupted `.kit-version` is the only way to reach it, and a 7+-character unknown string (`deadbeef12`) is fine (`git log deadbee..4cbe4f0`, exit 2).
*Action: implementer, before merge or in phase 2 with owner approval of the amendment: guard the hint (for example `"$recordedCommit"` with `$s.Substring(0, [Math]::Min(7, $s.Length))`), and add a test case for a short unknown recorded value on a real run. This is a one-line change inside the Phase 1 Territory.*

### F2 — Unknown recorded commit with no surgical file in the manifest: a NOTE followed by `Result: up to date`, exit 0 — MINOR

With a kit whose manifest has no surgical entry and an unknown recorded commit (probe `kitN unknown`, dry run and real), the output is the NOTE ("so every surgical file is listed as having no baseline - the verbatim files below could not be compared to a baseline either") and then `Result: up to date`, exit 0, and a real run still advances `.kit-version`. The plan (P3) says this is deliberate ("printed whenever the commit is unknown, including when the manifest has no surgical file"), so nothing is lost silently, but the NOTE speaks of surgical files that do not exist and sits above a green verdict; a wrapper matching `Result: up to date` still reads it as clean. The exit code is the existing rule (nothing pending). Real kits always ship surgical files, so this is test-fixture-shaped.
*Action: none required; owner may choose to reword the NOTE when `$surgicalFiles.Count -eq 0`.*

### F3 — A tree sha as the recorded value changes from "listed with commits" to "unknown" — ACCEPTED

`kitS treesha` (a tree sha in `.kit-version`): the parent printed the surgical file with the upstream commits (`git log` accepts a tree-ish), the tip prints the NOTE and `no baseline - review all`. Plan P1/Risks says a value `git log` could read is never reported as unknown; a tree sha is the one counterexample, already recorded in `notes.md` T002 ("`cat-file` 128, `git log` 0, unknown (not a commit)"). It is not a commit and cannot be a recorded kit commit, so the new behaviour is the correct one and the plan's sentence is slightly too strong.
*Action: none; optionally soften the Risks sentence in plan.md (an amendment needing owner approval, not worth one).*

### F4 — The stated limits are accurate but incomplete, and two notes numbers are stale — DOC DRIFT

What else reads an unknown recorded commit as "nothing changed" or as a degraded state, found by tracing the script:
1. `update-kit.ps1:240` the verbatim pass still reads each baseline with `git show "${recordedCommit}:$rel"`. The spec lists this as a stated limit and it is accurate: a failed read gives `$baselineText = $null`, and a file that differs from the kit becomes the `differs — no baseline (unknown provenance)` conflict (`:253`). The unlisted consequence: a verbatim file that is untouched since the recorded version (target equals baseline, which a known commit would clean-update and copy) cannot be recognised, so it is reported as a conflict needing `-Force`. Strictly "more conflicts", never "up to date", and the NOTE's phrase "the verbatim files below could not be compared to a baseline" covers it.
2. `$upToDate` (`:285`) now correctly includes the surgical entries; with no surgical file in the manifest it is still true (F2).
3. The "delivered once" NOTE condition (`:330`) is `$surgicalReport.Count -gt 0 -and -not $DryRun`, so with an unknown commit and no surgical file the record advances with no delivered-once warning (F2), and the NOTE it prints has the `Substring` defect (F1).
4. The spec (Assumptions) cites the unguarded `rev-parse HEAD` "at `:186`"; it is now at `:194` (and `$kitHeadSha` is used on `:331`). Harmless drift.
5. `notes.md` T004 says "the 22 verbatim conflicts as before"; the pre-spec measurement and the spec table say 21. `notes.md` T001 refers to "the byte comparison of T006", and phase 1 has no T006 (T005 holds it); T005 asks for a re-run of T001's states diffed against saved text, and `notes.md` records only that the seven test cases pass, not a saved-text diff (my own parent-versus-tip comparison over 16 states, above, covers that substance). T002 says the CI image's git is "the CI run of the branch", which has not happened yet.
*Action: implementer, at phase 2 notes: correct 22 to 21 (or state which measurement it is), the T006 reference, and record the CI run's git result; owner decides whether the byte-comparison claim of T005 needs a saved-output record.*

### F5 — Test gaps (the test is sound for what it covers) — MINOR

The seven cases pin the plan's states and each fails on the parent for the stated reason. Not covered: an unknown commit with a kit that has no surgical file (F2); a short or non-string unknown value on a real run (F1, which would have caught it); that a dry run leaves `.kit-version` byte-identical; that a known-but-behind real run advances the record. The real-run case asserts the advanced `kitCommit` and `delivered once`, which is the lost-report symptom, and is the right one. The `-Json` case asserts the key order with `Should -Be @(...)` on the property names, which is stable on PowerShell 7.
*Action: none required for merge; add the F1 case when F1 is fixed.*
