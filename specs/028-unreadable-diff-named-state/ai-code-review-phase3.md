## Findings

### F1 — "A trunk branch prints as before" is false when the trunk's diff is unreadable; the phase 1 review's F4 and notes.md say so, the flow-down note and the roadmap row do not — MINOR (documentation accuracy)

`adoption/updating.md` ("What does NOT change": "The output and exit code of every branch whose diff is readable, empty, has no base ..., is in a shallow clone with a base, or is a trunk branch's") and the GAP-034 inventory row ("An empty readable diff, a missing base, a shallow clone and a trunk branch print as before"). The dispatch reads the diff for every branch, trunk included, before the lane split, so on `main`/`master` an unreadable diff against the base changes the count line from `0 changed file(s)` to `diff unreadable (git diff exited 128)`. Reproduced (a trunk ahead of `origin/main`, unreadable `src` tree; old script `0 changed file(s)`, new script `diff unreadable`; verdict `OK` and exit 0 in both). The phase 1 review (F4) found this, and notes.md ("F4 stated") records it and says plan D3's "never reaches it" is true of the policy function and not of the count line; the two documents an adopter reads were written as if it were not so. The effect is cosmetic (no verdict, no exit change, no new line), but the note is where an owner looks to learn what may newly appear, and it lists a count-line change only for numbered branches.
*Suggested fix*: in the note, say the count line reads `diff unreadable` on any branch whose diff against the base cannot be read, trunk included, with the verdict and exit unchanged on trunk; reword "or is a trunk branch's" to "a trunk branch's verdict and exit code" in both places, and add it to the known limits or to "What an owner may newly see". Documents only.

### F2 — Limit (3) "none was found swallowing a failure" does not hold: two other `git` reads in the pack swallow a failing read, and one is a gate — MODERATE (documentation accuracy; a finding for a new roadmap row)

`adoption/updating.md` limit (3): "The pack's other `git` reads (`git log`, `git show --numstat`, `ls-tree`) are not changed; none was found swallowing a failure, but they were not audited"; the roadmap row says "(not audited)". plan.md's Risks section says that if the replay or the fixtures show one swallowing a failure, it becomes its own roadmap row; no row was opened. Probing the pack with a damaged blob (the object `git show --numstat` must read, which `git diff --name-only` does not) shows the claim is untrue: `Invoke-PhaseSizeWarningCheck` (`git show --numstat --format='' $commit 2>$null`, line 1284) and the Micro lane's phase walk (the same read, line 851) treat a failed read as zero lines. Reproduced on a numbered branch `002-b` whose single `phase 1` commit adds a 700-line `big.txt`: readable, the run prints `WARNING: PhaseSizeWarning: commit ... changes 700 line(s)`; with the loose blob of `big.txt` deleted, `git diff --name-only` still exits 0 (`1 changed file(s)`, no `DiffUnreadable`), `git show --numstat` exits 128, and the warning silently disappears. With a Micro declaration (`**Delivery Level**: Micro`, one 700-line commit) the readable run FAILS (`MicroLane: the phase's 1 commit(s) change 706 line(s) in total — ... at most 400 lines ... a hard bound`), and the damaged run prints `enforcement-pack: OK` (exit 0). That is the same class as GAP-034 (a git read that failed, read as an empty answer, a hard bound passes) reached through a different read, and the new reader does not cover it because the diff list is read cleanly. The other reads named in the limit were not probed one by one (`git log -z`, `ls-tree -r` of `specs`, `git show -U0`), but lines 472, 541, 1341, 1368, 1706, 1719 and 1511 have the same `2>$null` shape and no exit check.
*Suggested fix*: reword limit (3) in `adoption/updating.md` and the inventory row to say that `git show --numstat` in the Micro phase walk and the phase-size warning are known to read a failure as zero lines (a damaged blob turns the Micro 400-line failure into `OK`), and that the other reads of the pack were not audited; open a roadmap row (GAP-035) for the `--numstat` reads, as plan.md's Risks section prescribes, and say in notes.md that the replay and fixtures did not show it but this review did. Documents only; the script fix is a new feature.
