## Findings

### F1 — The flow-down note names "no base" as a condition that prints UNGRADED; at HEAD it does not — MINOR (documentation accuracy)

`adoption/updating.md`, "What it does now": "A Lite branch that touches one and cannot be graded (shallow clone, no base, an unreadable tree) prints an `UNGRADED:` line and still exits 0." With no `main`/`origin/main`, the Lite gate reads an empty changed-file list (`Get-ChangedFiles` returns nothing without a base and `$Base` is empty), so the amendment check is silent: I reproduced it (`docs/nobase` amending `001-a/plan.md`): the only lines are the existing no-base WARNING and `UNGRADED: ReviewProvenance`, nothing about the amendment. The script's own LIMITS comment says so ("or which has no diff base ... is not graded and says nothing for want of a gate"), limit (3) of the same note covers the empty-list case, and the adoption table at `adoption/updating.md:489` lists exactly the pre-existing UNGRADED lines for a missing base. The sentence overstates the safety net: an adopter with a truncated clone or an unrelated-history base is told the Lite amendment gets an UNGRADED line when it gets none. The roadmap row says "(shallow clone, unreadable tree)" and is correct.
*Suggested fix*: drop "no base" from that sentence and add it to limit (3) ("no diff base ... is not graded and prints as before"); amend notes.md if it repeats it. Documentation only.

### F2 — The replay's "Newly graded" column is inferred from output differences, so it misses newly graded commits that pass, and the "does not show" list omits that the adopted histories exercise none of the new path — MINOR (measurement honesty)

(a) The driver compares old and new output byte for byte; a commit that is newly graded and passes prints the same roll-up line (`graded N of M`) because the own-directory commit was already counted. The kit's own history holds such a case: merge `abb4d47` (branch `026-merge-commit-amendment-grading`) has two commits amending feature 025's plan with the owner's record and approver (`c64348c`, `71c1189`); the replay reports it identical (`graded 25 of 27`, exit 0 to 0) and the table's "Newly graded" for the kit is 2 (the two Lite runs). The spec's own table lists four merges amending another feature's documents (`abb4d47`, `22f2af4`, `c28a867`, `59deae2`); all four are newly graded by the new script, so the honest kit count is four branches (and, at commit level, seven commits: 2 + 3 + 1 + 1), not two. FR-010 and T017 ask for "commits newly graded"; the table counts runs whose output changed. It also hides the one case that answers "would an honest owner be blocked on a numbered branch": it passed. (b) I checked with git whether any merged branch in the three adopted clones changes another feature's spec document that exists at its base: none does (and no Lite branch changes any). So "106 byte-identical, including every adopted-project run" is true but shows only that the new code is silent where it has nothing to grade; it says nothing about the new path on adopted data. The note's "what it does not show" lists neither this nor the commit-level undercount.
*Suggested fix*: in notes.md T017 and the flow-down paragraph, rename the column "runs whose output changed", state that a newly graded commit that passes prints the same output, name `abb4d47` as the passing case, and add "the three adopted histories contain no amendment of another feature's approved document, so their runs exercise none of the new path". Optionally count commits from `git log --name-status` over each range. No re-run needed for the first two.

### F4 — "109 named a branch" mixes two things, and one real feature merge is not in the 109 — NIT

The 28 unreplayed merges are 19 in the kit (eighteen `main` or `origin/main` merged into a branch or into main, mostly inside their branch's range, and `46ba9bb` "Merge 021-developer-roster: ...", a merge of a numbered feature whose subject the driver's two patterns do not match) plus 9 in the adopted clones (5 `main`-into-branch in FitForge, 4 `governance:`). The notes say "subject names no branch (a main merged into a branch, governance: merges)"; the 021 merge is neither. The numbered count (36) therefore omits one real feature merge; the effect on the measured result is unknown (I did not replay it).
*Suggested fix*: say "109 matched the two subject patterns" and list `46ba9bb` as unreplayed; optionally replay it by hand.

### F5 — Timing claim is stronger than a single, order-biased sample supports — NIT

"The check costs no measurable time" and "no slower on any of the four largest runs": one sample per version per merge, old always run first (the new run follows with a warm object cache). The four largest by commit count (50, 49, 29, 28 commits, all in the kit) are indeed faster for the new script, but a different reading of "largest" gives a slower new run (FlowBoard 18 commits: 6.03 s old, 6.21 s new, +3%; FitForge 3 commits 1.11 s vs 1.17 s). The script's own comment quotes about 100-200 ms per merge for the tree reads. The claim is probably true; it is not demonstrated.
*Suggested fix*: "within noise on a single sample per run, old run first" instead of "no measurable time".

### F6 — "One verbatim file" understates what flows down; the Lite sentence goes beyond T014's wording — NIT (both disclosed or minor)

(a) The note says "One verbatim file: `scripts/enforcement-pack.ps1`, plus this document and `docs/sdlc/branch-strategy.md`". `kit-manifest.json` classes all three as verbatim (`scripts/*.ps1`, `adoption/**`, `docs/sdlc/branch-strategy.md`); 026's note says "Three verbatim files". The sentence lists the right files, the count is the oddity. (b) T014 and plan D11 say "edit only the sentences found false" in `branch-strategy.md` and `critical-delivery.md`. T013 found none false; the implementer added one sentence and one marker to `branch-strategy.md` on FR-014's ground and flagged it in notes.md. I agree the sentence is correct (it matches the D1/D2/D6 behaviour: "approved" = exists at the base, "owes the record and the approver in the commit message", "a branch that changes no such file is not asked for anything"), within Territory, and the digest text is 107 characters. It is a step past the task wording; the owner should acknowledge it rather than the plan being silently stretched.
*Suggested fix*: (a) "Three verbatim files". (b) None beyond the owner's explicit acknowledgement at merge.

### F7 — Feature 026's flow-down note still says the Lite lane runs no amendment check — INFO
