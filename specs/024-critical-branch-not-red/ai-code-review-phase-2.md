## Findings

### F1 — "Committing the artifact early turns the branch red for the rest of the feature" is broader than the code — DOC DRIFT

The sentence appears bolded in the flow-down note ("What an owner may newly see"), in critical-delivery.md ("committing the artifact early turns the branch red for the rest of the feature"), in the digest marker `Committing the Critical independence artifact early turns the branch red from then on` (adoption-digest.md), and in plan Risks. What the code does: once the artifact is committed at `HEAD`, `Get-CriticalMergeReadiness` returns not pending, and the ARM grades it, exactly as before. A VALID artifact then passes. The kit's own fixtures say so: `CRIT-R01/pass-artifact-committed-mid-feature` ("Team arm, tip at phase 2 of 3, with a VALID human review committed: nothing is pending, no WARN, the arm grades the artifact and passes", exit 0) and `CRIT-R01/pass-solo-artifact-old-mid-feature` (a solo artifact older than 24 hours passes mid-feature). So the branch is red from the early commit only until the artifact is valid (team arm: provenance filled, reviewer not the owner, on the roster) or, in solo, until 24 hours after its first commit. The explanatory clause beside the bold sentence ("once it exists the arm grades it, and the solo arm's cooling-off clock starts at that commit") is accurate; the headline over it is not, and the digest marker, which is what an owner reads first, carries only the headline. The likely real-world case behind it (a template or half-filled review committed early) is red until finished, which is a different and shorter claim than "the rest of the feature". It errs on the cautious side, but an adopter deciding whether to commit a finished review early is told something false, and this kit's rule is that a claim means what the code does.
*Action: implementer reword in all four places (note, critical-delivery.md, digest marker, plan Risks) to: committing the artifact early ends the pending state, so the arm grades it from then on; an unfinished or invalid file (team) or one under 24 hours old (solo) fails; a valid one passes. Rebuild the digests with `scripts/build-digests.ps1`. A plan Risks edit is an amendment and needs the approver line (constitution I).*

### F2 — "never a pass it should not have" contradicts the first limit it follows — DOC DRIFT

critical-delivery.md and the flow-down note state limit 1 (a final commit not read as final, with no artifact committed, still reads as mid-feature and stays on the WARN: a WARN where the old code failed, i.e. a pass the check should not give), then limit 2, which ends: "Strict is the safe direction: the cost is relief the feature does not get, never a pass it should not have." Read together, that last sentence is false for the feature as a whole, because limit 1 is exactly a pass it should not have; it holds only for the out-of-order stretch that limit 2 is about. The phrase "defeat the heuristic in both directions" in the same paragraph then explains only the strict direction (the other direction offered is a rule the kit did not adopt), so the reader cannot tell what the second direction is. The script header (lines 332–341) and plan Risks word limit 2 correctly, scoped to "that stretch"; the user-facing pages are looser. A related softer drift: DoD item 6 and critical-delivery.md say the check warns "while the branch is **provably** mid-feature", but "mid-feature" is inferred from one incidental phase token (round-4 F3, plan D3: "deliberately weak"); the word `provably` claims a proof the heuristic does not give. The flow-down note itself uses "provably", too.
*Action: implementer scope the safe-direction sentence to limit 2 ("for this limit, the cost is relief the feature does not get, not a pass it should not have; limit 1 is the opposite and is covered by gate 6"), say which two directions are meant or drop "in both directions", and replace "provably" with "shown by the heuristic below to be" (or equivalent) in DoD item 6, critical-delivery.md and the note. Rebuild digests if a marker changes.*
