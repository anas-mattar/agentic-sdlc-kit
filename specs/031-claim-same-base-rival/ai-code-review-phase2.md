## Findings

### F1 — Roadmap closes GAP-037 and ships the row without the open limit or the pending gate — DOC DRIFT

`docs/roadmap.md:66` (the GAP-037 status text) says "closed by kit feature 031", and `:104` marks the row `shipped`, but neither records what stays open or what is still to come. Feature 030's text, which this one is modelled on, ended with "**Open, by decision:** ..." and "Built and measured; the fresh-context AI review of each phase, the owner's gate and the human review at merge are still to come". Here: (a) the limit the owner approved in the spec (two claimants creating the ref at the same moment where our push exits non-zero are not told apart, the review's F2) is not in the inventory text and appears in the log (`:696`) only as "the limit ... was stated"; (b) T011 (the final isolated-checkout run on the final commit) is open and the owner's gate and the human review are not done, which the text does not say; (c) the log says the harness "1809 on the phase 1 commit" where notes T007 measured a detached worktree of the parent with the changed files copied in, not a checkout of `894f101`. Nothing here is false in what it says, but "closed" and `shipped` read stronger than the repository supports today, and a reader of the inventory will not learn the one known residual case.
*Action: implementer to add to line 66 an "Open, by decision" sentence naming the simultaneous-create limit and a closing "built and measured; T011, the owner's gate and the human review at merge are still to come", and to say "phase 1 working tree" in the log, in a follow-up docs commit before merge; the owner decides whether the row stays `shipped` before the gate (030 precedent: yes).*

### F2 — "If a claim ends in the warning, nothing needs doing" is wrong on the third consecutive loss — MINOR

`adoption/updating.md:1462`: "If a claim ends in `claimed concurrently by a claimant of the same short name`, it was renumbered for you: nothing needs doing". The warning is printed before the attempt-limit check (`claim-feature.ps1:195`, then `:206-208`): when the last of `$MaxAttempts` attempts (three) also reaches the same-name state, the output contains that warning and the script then refuses with `Lost the allocation race 3 times — renumber manually`, exit 1, leaving the local branch and its spec directory. The note's "What does NOT change" mentions the three-attempt loop but never says that the same-name state can end in that refusal. The state is practically hard to hit (each attempt needs a new same-name rival at the new number), and the harness cannot reach it (the dropped CLF-019).
*Action: implementer to reword to "if the claim goes on to say `CLAIMED:`, it was renumbered for you ... (a third consecutive loss ends in the existing `Lost the allocation race 3 times` refusal)"; no code change.*

### F3 — The note contradicts itself on "nothing moved" and quotes one form of the warning — MINOR

(a) `updating.md:1450` ends: "A claim with no rival, with `-NoPush`, ..., and each refusal of features 023 and 030 print what they printed before", and `:1454` says "On a claim with no same-name rival: nothing, byte for byte", while the same paragraph then says one refusal's quoted git text moved. The first sentence is true of the script's own sentences only. (b) The warning is quoted without its second form: with a numeric rival on the ledger as well, `$also` adds `; so did <rivals>` inside the parentheses (`claim-feature.ps1:194-195`). The note and `CLF-018` do not mention it (phase 1 review F6 noted no fixture exists), so a wrapper that matches the quoted text exactly misses that form. Also the note says the text is "not machine-parsed" (limit 4), which softens it.
*Action: implementer to say "except the git text quoted inside a rejected push's refusal (below)" in the two sentences and to add "; so did <other branches>" as a possible tail of the warning.*

### F4 — Feature 030's unqualified limit is left standing next to this one — DOC DRIFT

`adoption/updating.md:1421-1444` (030's note) still says "two claimants who chose the same number and short name from the same `main` tip hold branches at the same commit, and their pushes behave as they always did". This feature changes that statement for the exit-0 case, and the new note's limit 1 says it "narrows, and does not remove" it, but does not say 030's sentence is superseded in that respect, as 030's own note did explicitly for 023's limits paragraph. An adopter reading 030's note alone is told the state is unhandled.
*Action: implementer to add one sentence to the new note: "This supersedes the last sentence of limit (1) of feature 030's note above, which stands as history and is not edited", with the same care not to alter 030's text (and no digest marker).*
